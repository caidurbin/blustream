# HA integration: library owns the protocol, integration is a thin HA mapper

All protocol-shaped logic — wire formatting, response parsing, type conversion of device fields into Python primitives — lives in the `blustream` PyPI library, not in the Home Assistant integration. The integration imports `DMP168` from the library and calls typed methods (`await device.get_uptime() -> timedelta`, `await device.get_status() -> SystemStatus`, etc.); it does not call `execute_command("uptime")` and parse the raw `DDDD:HH:MM:SS` string itself. Where the library does not yet expose a typed helper the integration needs, the library is extended first (in a tagged release with its own PyPI publish) and the integration then bumps its pinned dependency to consume the new API. This is mandated by HA's code-review rule (`developers.home-assistant.io/docs/creating_component_code_review` §4): *"All API specific code has to be part of a third party library hosted on PyPi. Home Assistant should only interact with objects and not make direct calls to the API."* The integration's allowed responsibilities are: config flow, coordinator wiring, entity-shape mapping (e.g., `timedelta` → `datetime` via `dt_util.utcnow() - delta`), device-registry construction, diagnostics, repair issues, and translations. Anything that touches a wire byte belongs in the library. Serialization of device-status objects for diagnostics (e.g. `SystemStatus.to_dict()`) is library-side too: it shares the protocol's field shape and the cross-language parity contract (the same shape `format_status()` emits for the CLI `--json` surface), so the integration consumes a ready-made primitives dict rather than calling `dataclasses.asdict()` on a library object.

The library and the HA integration release on **independent semver**, not in lockstep. The library may cut a patch (`v0.1.1`) for a library-only bugfix without forcing an integration release; the integration cuts its own releases whenever it consumes a new library API or changes its own HA-shape behavior. The integration's `manifest.json` always pins the library exactly (`blustream==X.Y.Z`) per HA convention. This differs from the codegen-driven coordination in ADR 0007, which couples the spec, the Python library, and the Lua driver because they share generated artefacts — the HA integration shares no generated artefacts with the library, only a Python API, so the looser coordination fits.
