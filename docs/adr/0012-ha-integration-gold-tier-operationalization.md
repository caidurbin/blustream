# HA integration: operationalizing the gold-tier commitment

ADR 0009 commits the HA integration to the Gold tier of HA's Integration Quality Scale from v0.1. This ADR captures the concrete operational choices that flow from that commitment, in one place, because several of them have surprise-without-context risk for future contributors.

**Test location.** Integration tests live at the repository top-level path `tests/integration/`, not nested under `custom_components/blustream/tests/`. The nested layout would be the obvious choice but it conflicts with `hassfest` — HA's manifest/translations/config-flow linter trips on test files inside the integration directory. The canonical `hacs/integration` validation workflow does `rm -rf tests` (its own step comment: "Test files conflict with running hassfest") immediately before invoking `home-assistant/actions/hassfest`. Top-level placement is the HA convention itself: HA core keeps tests at `tests/components/<domain>/`, never nested inside `homeassistant/components/<domain>/`, and `hacs/integration` (a real `custom_components/hacs/` integration) likewise keeps `tests/` at the top level. The existing top-level `tests/` directory continues to hold library-only tests; `tests/integration/` is the HA-only sibling under the same root, so the hassfest exclusion is one path.

**Test coverage targets.** Two thresholds: **100 %** on `custom_components/blustream/config_flow.py` per the Gold rule `config-flow-test-coverage` (every step, every error branch, every reconfigure/reauth/options flow if added); **≥95 %** on every other integration module per the Silver rule `test-coverage`. The split is non-obvious — the config-flow rule is stricter than the general one.

**CI tooling.** Three GitHub Actions workflows specific to the integration, each pinned to one HA version (HA-version matrices are not idiomatic for custom integrations because `pytest-homeassistant-custom-component` pins one HA version per release, so a matrix tests PHCC versions rather than real-world HA variance): the test workflow runs `pytest tests/integration/` with PHCC + syrupy; the validate workflow runs `home-assistant/actions/hassfest@master` and `hacs/action@main` with `category: integration`; the validate workflow runs on push, PR, **and** a daily `schedule: cron` (universal pattern in surveyed HACS integrations — catches HA-side breakage that lands between PRs).

**Manifest fields beyond the obvious.** `"loggers": ["blustream"]` declares the library's logger namespace so HA's debug-logging UI wires into the library's log lines, not just the integration's — without it, users enabling debug logging on the integration see only HA-shape messages and miss the protocol-level detail that's usually the bug. `"version": "0.1.0"` and the config-flow class's `VERSION = 1, MINOR_VERSION = 1` ship from v0.1 so future `async_migrate_entry` upgrades have version numbers to bump against. `dhcp` and `zeroconf` blocks are declared per ADR 0010.

**Library packaging — `py.typed` marker.** The `blustream` library ships a `py.typed` marker file in v0.1.0. Library API surfaces are fully type-annotated. Adding `py.typed` later is a breaking-ish change for downstream consumers — sudden flood of type errors when they enable `mypy --strict` against the now-typed library. Cheaper to ship it from v0.1.0 even though Platinum's `strict-typing` rule isn't committed to yet, because doing so leaves Platinum reachable without a library-side breaking change later.

**Quality-scale registry.** The integration ships `custom_components/blustream/quality_scale.yaml` declaring per-rule compliance (`status: done | exempt | todo` + `comment:` per rule). `stale-devices` is declared `exempt` (1:1 entry-to-device — see Q12 grilling transcript / future ADR if revisited). Silver `log-when-unavailable` and `entity-unavailable` are declared `done` and satisfied transitively by the coordinator + `CoordinatorEntity` pattern.

**Reserved-for-future (Platinum).** `inject-websession` (accept an injectable `aiohttp.ClientSession` for HTTP integrations) does not apply to v0.1 — we use TCP, not HTTP. Flagged here because if a future entity (e.g., volume control via web-GUI scrape, or a richer device-status surface) ever requires HTTP, that API should be designed to accept an injected session from day one — retrofitting later is painful.
