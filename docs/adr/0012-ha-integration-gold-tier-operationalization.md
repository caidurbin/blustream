# HA integration: operationalizing the gold-tier commitment

ADR 0009 commits the HA integration to the Gold tier of HA's Integration Quality Scale from v0.1. This ADR captures the concrete operational choices that flow from that commitment, in one place, because several of them have surprise-without-context risk for future contributors.

**Test location.** Integration tests live at the repository top-level path **`tests/components/blustream/`** — the exact convention HA core uses for `tests/components/<domain>/` (never nested inside `homeassistant/components/<domain>/`). The nested-under-the-integration layout (`custom_components/blustream/tests/`) is the obvious-but-wrong choice: hassfest's manifest/translations/config-flow linter trips when a test package sits *inside* the integration directory it's linting. A top-level `tests/` sibling, by contrast, validates cleanly — hassfest doesn't walk arbitrary paths. The `rm -rf tests` step folklore comes from HACS's own backend-repo workflow (the `hacs/hacs` integration's CI), not from `hacs/action` (which does not invoke hassfest at all). The existing top-level `tests/` directory continues to hold library-only tests (and the live-hardware `tests/integration/` suite stays untouched); `tests/components/blustream/` is the HA-only sibling under the same root. This name is preferred over `tests/integration/` because the live-hardware path already claims that name, and because `tests/components/<domain>/` is the universally recognized HA-core convention.

**Test coverage targets.** Two thresholds: **100 %** on `custom_components/blustream/config_flow.py` per the Gold rule `config-flow-test-coverage` (every step, every error branch, every reconfigure/reauth/options flow if added); **≥95 %** on every other integration module per the Silver rule `test-coverage`. The split is non-obvious — the config-flow rule is stricter than the general one.

**CI tooling.** Two GitHub Actions workflows specific to the integration, each pinned to one HA version (HA-version matrices are not idiomatic for custom integrations because `pytest-homeassistant-custom-component` pins one HA version per release, so a matrix tests PHCC versions rather than real-world HA variance): the test workflow runs `pytest tests/components/blustream/` with PHCC + syrupy; the validate workflow runs `home-assistant/actions/hassfest@master` and `hacs/action@main` with `category: integration`; the validate workflow runs on push, PR, **and** a daily `schedule: cron` (universal pattern in surveyed HACS integrations — catches HA-side breakage that lands between PRs).

**Manifest fields beyond the obvious.** `"loggers": ["blustream"]` declares the library's logger namespace so HA's debug-logging UI wires into the library's log lines, not just the integration's — without it, users enabling debug logging on the integration see only HA-shape messages and miss the protocol-level detail that's usually the bug. `"version": "0.1.0"` and the config-flow class's `VERSION = 1, MINOR_VERSION = 1` ship from v0.1 so future `async_migrate_entry` upgrades have version numbers to bump against. `dhcp` and `zeroconf` blocks are declared per ADR 0010.

**Library packaging — `py.typed` marker.** The `blustream` library ships a `py.typed` marker file in v0.1.0. Library API surfaces are fully type-annotated. Adding `py.typed` later is a breaking-ish change for downstream consumers — sudden flood of type errors when they enable `mypy --strict` against the now-typed library. Cheaper to ship it from v0.1.0 even though Platinum's `strict-typing` rule isn't committed to yet, because doing so leaves Platinum reachable without a library-side breaking change later.

**Quality-scale registry.** The integration ships `custom_components/blustream/quality_scale.yaml` declaring per-rule compliance (`status: done | exempt | todo` + `comment:` per rule). `stale-devices` is declared `exempt` (1:1 entry-to-device — see Q12 grilling transcript / future ADR if revisited). Silver `log-when-unavailable` and `entity-unavailable` are declared `done` and satisfied transitively by the coordinator + `CoordinatorEntity` pattern. The v0.1 sign-off bar is *no `todo` on any Gold-or-below rule*; rules above the committed tier (Platinum) may legitimately carry `todo` (applicable but deferred — e.g. `strict-typing`) or `exempt` (genuinely N/A — e.g. `inject-websession`). hassfest enforces only rules at or below the declared `quality_scale: gold`, so an above-tier `todo` neither fails validation nor weakens the Gold claim.

**Reserved-for-future (Platinum).** `inject-websession` (accept an injectable `aiohttp.ClientSession` for HTTP integrations) does not apply to v0.1 — we use TCP, not HTTP. Flagged here because if a future entity (e.g., volume control via web-GUI scrape, or a richer device-status surface) ever requires HTTP, that API should be designed to accept an injected session from day one — retrofitting later is painful.
